# Jev 机器人指令台

用游戏模拟的方式，在 Web 页面里指挥一台桌面陪伴机器人。

指令链路：**语音转写文本 → Jev 决策模型 → 确定性动作编排 → 机器人执行**

机器人形态：云台头部 + 屏幕表情 + 双机械臂 + 移动底盘 + 声音反馈。

---

## 这不是 LLM：Jev 是什么

[Jev](https://thejevai.com/docs) 是 TypeSafe 的**非生成式决策模型**（System One model），
2026 年 9 月发布，托管在 OpenRouter 与 TypeSafe 官方 API。

关键区别——这决定了整个工程的架构：

| | 生成式 LLM | Jev |
| --- | --- | --- |
| 输出 | 文本 / JSON 字符串 | **定型值 + 概率分布** |
| 可能说错吗 | 会，可能编造 | 不会，只能从你给定的选项里选 |
| 不确定性 | 藏在文字里，看不见 | **就是返回值本身，可直接设阈值** |
| 价格 | 输入输出都计费 | $0.042/百万输入 token，**输出免费** |

所以本工程**不让 Jev 生成任何文字**。它只回答三个定型问题：

| 问题类型 | 用途 | 返回 |
| --- | --- | --- |
| `choice` | 从 ≤255 个选项中选一个 | `choice` + `probabilities` + `confidence` |
| `score` | 在 2~10 个有序档位上评分 | `score`（可落在档位之间）+ `legend` + `probabilities` + `confidence` |
| `noul` | 判断某个命题成立的概率 | `noul`（0~1），**没有独立的 confidence 字段** |

于是职责划分变成官方推荐的 *route-then-write* 模式：

```
Jev（判定）      →  用户想要什么？能不能做？要不要反问？多急？
我的代码（执行） →  这个意图对应哪串动作、说什么话术、给哪些追问按钮
```

**动作编排和话术全部由代码决定**，不依赖任何生成式输出，因此行为可预测、可测试、可调参。

## 一次决策问了 Jev 三个问题

全部并行评估，单次往返拿到全部答案：

| 问题 key | 类型 | 作用 |
| --- | --- | --- |
| `intent` | choice | 27 个受支持意图中选一个，附带完整概率分布 |
| `safe_to_execute` | noul | 安全闸门：当前能否安全执行 |
| `gesture_style` | choice | 表现风格：gentle / normal / lively / solemn |

### 为什么只有三个

官方文档明确要求各问题的含义**彼此独立**，不做重复提问：

- **`intent` 的 confidence 已经表达了不确定性**，无需再单独问一次"信息是否充分"。
  官方也特别指出 noul ≈ 0.5 表示"不知道"，应作为第三种结果处理——
  这个职责由 intent 的概率分布天然承担。
- **情绪不再单独提问**：27 个意图里大部分已隐含情绪（greet→happy、dance→joy），
  单独再问一次是浪费决策预算。
- **`gesture_style` 与 `intent` 正交**：同一个意图可以有不同表现力，
  例如"跳舞"可以轻快也可以夸张。它真正参与调度——
  gentle 把力度参数收敛到 0.7 倍并放慢到 1.1，lively 放大到 1.25 倍并加快到 0.85，
  影响动作幅度、节奏与表情。次数与保持时长属语义，不参与缩放。

情绪由 `意图 + 风格` 在代码中推导，不消耗额外决策。

## 决策策略

Jev 的 `confidence` 衡量的是**概率分布的集中度，不代表正确率**。
按官方建议，阈值由应用按自身风险自定。配置页可实时调整：

```
safe_to_execute noul < 0.40          →  安全闸门拦截，只做拒绝回应
safe_to_execute noul ∈ [0.40, 0.60]  →  判定不确定，反问确认（不当成不安全）
safe_to_execute noul > 0.60          →  放行，继续走下面的置信度分支

intent confidence < 0.45             →  按未知意图处理，给引导选项
intent confidence < 门槛              →  置信度中等，反问确认
intent confidence ≥ 门槛              →  直接执行
                                    门槛 = 0.70（普通）/ 0.85（高风险）
```

### 为什么 noul 是三段而不是一刀切

官方明确指出 **noul ≈ 0.5 表示"不知道"**，应当作为第三种结果处理。
只用一个 `safetyThreshold` 的话，`noul = 0.55` 会被判成"不安全"，
机器人就会无缘无故拒绝合理请求。因此摇摆区间单独成一段，判定为不确定时改为反问。
判定面板把这段画成轨道上的斜纹带，一眼看出 noul 落在哪一侧。

### 为什么执行门槛按风险分档

问一句"你能做什么"和让机器人移动，副作用差一个量级。
`PLANS` 里每个意图都声明了 `risk`：

| risk | 含义 | 门槛 |
| --- | --- | --- |
| `none` | 无副作用（问候、表情、闲聊） | 0.70 |
| `low` | 局部动作（取物、拍照） | 0.70 |
| `high` | 会移动（过来、跟上、转身） | 0.85 |

### 硬件缺失时的降级

`requires` 声明与编排实际用到的执行器由测试强制对齐
（`npm test` 第 8 组）。主动作被硬件约束剔除时走 `degraded` 分支：
不再说"来啦来啦"却原地不动，而是讲清缺什么，并尽量演出仍做得到的部分
（缺底盘时至少转头看向用户）。

## 三个问题不能互相引用

Jev 的多个问题是在**同一个 state 上并行评估**的，彼此看不到对方的答案。
因此后两个问题**不得引用 `intent`**——它不在 state 里，引用了模型也只能靠猜。

安全闸门要回答的是"这件事做不做得了"，而"这件事需要什么硬件"这个信息，
改由 `buildState()` 自行推断、以 `requested_capabilities` 放进 state：

```json
"requested_capabilities": {
  "capabilities": ["mobility"],
  "source": "inferred",
  "available": ["camera", "speaker", "mobility", "arm"]
}
```

判定面板的「判定输入 state」里也列出这一行，
配合硬件开关可以直接看到因果：需要的能力不在 `available` 里时 noul 就会掉下来。
`npm test` 第 14 组会检查三个问题的 instructions 只引用 state 中真实存在的字段。

### 三种提问类型的判读方式

**noul ≈ 0.5 是"我不知道"，要当成第三种结果处理。**
不是 0 也不是 1 时，说明 Jev 在两个方向间摇摆——此时应当反问，而不是硬选。

**confidence 高不代表对。** 一个模型把全部权重压在一个选项上，confidence 就是 1.0。
是否选对了，取决于你的 `criteria` 描述写得好不好。

**score 的 score 是概率加权平均**，可落在档位之间。

## 接入真实 Jev

### 配置方式：`.env`（推荐）

项目根目录已有 `.env`（已加入 `.gitignore`，不会被提交），把密钥填进去即可：

```
JEV_API_KEY=sk-or-v1-你的密钥
JEV_UPSTREAM=https://openrouter.ai/api/alpha/decisions
JEV_DEFAULT_MODEL=typesafe/jev-1.13
JEV_PROXY_PORT=8787
```

填完后启动两个进程：

```bash
npm run proxy       # 终端 1：读 .env，监听 8787
npm run dev         # 终端 2：前端，启动时自动向代理拉取配置
```

前端启动时会向代理的 `/jev/config` 请求密钥、端点、模型，
**检测到有效密钥后自动切换到真实模式**，界面上无需任何设置。

`.env` 是唯一真源——浏览器不落盘密钥，也不需要手工填写。
配置页的「从 .env 加载」按钮可在代理启动后手动重新拉取。

### 端点对照

| 服务 | 端点 | 模型名 | key 前缀 |
| --- | --- | --- | --- |
| OpenRouter | `https://openrouter.ai/api/alpha/decisions` | `typesafe/jev-1.13` | `sk-or-v1-` |
| TypeSafe 官方 | `https://api.typesafe.ai/v1/systemone` | `jev-latest` | `sk_` |
| 本地代理 | `http://localhost:8787/jev/decisions` | 同上 | 服务端持有 |

换服务商只需改 `.env` 里的 `JEV_UPSTREAM` 与 `JEV_API_KEY`，前端零改动。

### 不用代理的直连方式

配置页填入 API Key 即可，但**密钥会出现在浏览器里，仅供本地调试**。

### 代理端点

| 端点 | 用途 |
| --- | --- |
| `POST /jev/decisions` | 透传转发到上游 Jev，响应原样返回 |
| `GET /jev/config` | 下发 `.env` 中的密钥、端点、模型 |
| `GET /health` | 健康检查，查看是否已加载密钥 |

代理在转发前会校验请求体（state / questions 结构、问题类型、score 档位数量），
不合规直接返回 422，避免无谓的计费请求。

> `/jev/config` 会下发密钥，仅适用于绑定 localhost 的本地开发。
> 部署到公网前务必加上鉴权或移除该端点。

### 验证脚本

```bash
npm test          # 428 项离线断言，不消耗额度
npm run test:live # 48 个用例打真实 API（约 $0.004）
```

`npm test` 覆盖：

- 意图体系三方对齐（枚举 / criteria / 编排）
- 动作库引用完整性，**反向检查死动作**
- 全部 28 个意图的编排可生成、参数合法、**无重复动作**
- **`requires` 声明与编排实际用到的执行器对齐**（含 risk 分级）
- **硬件缺失时拒绝话术说清缺什么**、降级路径保留可执行的部分
- **noul 三态**：拦截 / 摇摆反问 / 放行，含区间边界
- **风险分级门槛**：高风险意图用更严的执行门槛
- **非法 choice 的置信度回收**：不沿用为非法选项算出的 confidence
- **表现风格作用方向**：lively 放大力度且加快，而非一味放慢
- **停止指令抢占**与优先级参与调度
- **state 与问题自洽**：instructions 只引用 state 真实存在的字段
- **摇摆区间配置校验**：非法区间回落默认
- Mock 与真实协议形状一致性，概率分布和恰为 1
- 模型输出的类型收敛（confidence / noul 上下界）

`npm run test:live` 直接复用 `src/` 的代码构造请求打真实 API，
覆盖全部 28 个意图 + 安全闸门 + 兜底场景，并打印每次调用的花费。

> 不要另写一份请求的副本用于验证——副本会与实现漂移，导致结果不可信。

## 故障排查

| 脚本 | 作用 |
| --- | --- |
| `npm run check:css` | 校验 CSS 花括号配平与 `@media` 块闭合 |

CSS 结构损坏时 `tsc` 与 `vite` 都不会报错，但会导致整段样式在特定断点下静默失效，
因此已挂到 `build` 之前。

### 直连报 401 `No cookie auth credentials found`

这是 **OpenRouter 在没收到 `Authorization` 头时回退到 cookie 鉴权的提示**，
不代表密钥写错，而是请求压根没带密钥。常见成因：

1. 先用本地代理跑过（配置里被标记为 `.env` 管理、密钥字段被清空），
   之后把端点预设切成了 OpenRouter，但那个标记残留了下来。
   **现在的处理**：是否走代理由「当前端点」当场判定（`isProxyEndpoint`），
   不再读 `proxyManaged` 这个历史标志；切到非代理端点时界面也会自动展开密钥输入框。
2. 直连模式下密钥为空。**现在的处理**：请求发出前就拦下，直接给出
   「未配置 API Key，请在配置页填写 … 对应的密钥（或改用本地代理）」，
   而不是把上游那句与真实原因无关的 401 透传出来。

排查看「原始报文」→ 请求头：正常应能看到 `Authorization: Bearer sk-or-…xxxx`（已脱敏）。
走代理时这里**不该**出现 Authorization，密钥由服务端注入。

## 界面说明

三栏布局，右列顶部有五个页签：

| 区域 | 内容 |
| --- | --- |
| 左 · 舞台 | SVG 实时姿态：头部、机械臂、夹爪、底盘、表情、坐标网格，附姿态读数 |
| 中 · 对话 | 语音输入、快捷指令、预设 choice、决策路径、动作编排标签 |
| 右 · Jev 判定 / 动作库 / Jev 配置 / Jev 文档 / 选型思考 | 顶部横向页签切换；底部常驻执行轨迹 |

### 为什么是这五个页签

判定概率分布、动作库、模型配置、协议速查、选型取舍都是"看板型"内容，
**谁也不需要在同一时刻参照另一个**，所以合并成一列切着看，把整块水平空间让给舞台。

舞台必须独占左列且拿最大宽度——从动作库点一个动作时，机器人姿态要留在视野里。
这正是动作库**不能**放在左列的原因：放左边虽然更宽，但点动作时画面会被顶掉，
无法一边点一边看效果，等于丢掉了动作库"单独调参"的主要用途。

### Jev 文档页签

一页速查：Jev 是什么、state 的输入边界、三种提问类型怎么选、概率怎么读、
本工程的判定链与错误码表，末尾附官方出处链接。
只收"改这个工程时会用到"的部分，细节以官网为准。
`?tab=docs` 可直接定位到这一页。

### 选型思考页签

讲本项目为什么这么选：已兑现的优势、真实存在的代价、现状判断与后续方向。
和文档页的分工是——文档页答"Jev 怎么用"，这一页答"为什么用、代价是什么、往哪走"。
`?tab=tradeoff` 可直接定位。

### 判定面板

判定面板是全局信息密度最高的区域，因此右列给足宽度、判定区 `flex: 1`
吃掉面板剩余高度——面板越高，概率条就越长，不靠缩字号塞内容。

**阈值刻度线**直接画在概率条轨道上（默认 0.45 反问 / 0.70 执行，随配置页实时变化），
一眼看出选中项的权重落在哪一侧、为什么走「直接执行」而不是「反问确认」。
概率条按**绝对概率**绘制而非相对峰值——峰值归一化会把 0.01 的项也画成满格，反而误导。

`intent` 一共 27 个候选，面板展示概率最高的 12 项，其余折叠成一行汇总并给出合计权重，
不会让人误以为模型只评估了这几项。

判定结果下方的「判定输入 state」列出这次真正喂给 Jev 的输入变量
（用户原话、距离、电量、是否忙碌、当前动作、环境描述、硬件可用性），
字段名与 `buildState()` 送进 prompt 的完全一致，不在 UI 里另造一套说法。
配合配置页的硬件开关可以现场演示安全闸门：关掉「移动底盘」，
`hardware` 一行立刻变红，`safe_to_execute` 的 noul 掉到 0.12，机器人只做拒绝回应。

### 原始报文

判定面板顶部的「原始报文」开关，展开后**顶部直接摊开** URL、状态码、耗时、重试次数
与请求头，下面只用两个页签切换请求体 / 响应体这两块长文本：

| 位置 | 内容 |
| --- | --- |
| 顶部（不折叠） | 方法 + 状态码、请求 URL、总耗时、首字节耗时、重试次数、实际请求头 |
| 页签 · 请求体 | 本次真正发出去的请求体原文 |
| 页签 · 响应体 | 上游返回的响应体原文 |

关键在于**这几份数据取自真正发出去的那一次调用**：请求体是发送前序列化的原文，
响应体是未经 `JSON.parse` 加工的响应文本，都由 `JevClient` 在调用时记录、
随判定结果一起返回。界面不重新拼一份副本——副本会与实现悄悄漂移，
那这个视图就失去了"看原始数据"的意义。

JSON 只做「2 空格缩进重排 + 最轻的着色」，保留 `{}` `[]` 的原始结构，
不做逐项折叠、也不拆成自绘的 DOM 树——那样反而看不出层次，也不好框选复制。

失败时同样保留请求与响应，因为出错场景下"到底发了什么、上游回了什么"最需要看，
只给一句错误信息等于把排查线索丢掉。

密钥始终脱敏（只留前 6 位与后 4 位）：走代理时不发 `Authorization`，
直连时请求头里展示的也是脱敏后的值。

Mock 模式下这个视图同样可用，URL 会显示为 `mock://jev/local`，耗时标记为 0。

## 动作库

29 个预置动作，按执行器分组：头部 / 屏幕 / 机械臂 / 底盘 / 声音 / 身体。

点击动作库里的任意卡片可直接播放，绕过决策层，用于单独调参。

面板顶部的**搜索框**按动作名、id、别名过滤（如输入「点头」或 `nod`）；
**紧凑 / 宽松**切换排列密度——紧凑级把动作压成单行 chip 并按执行器分组横向排开，
29 个动作在 1440×900 以上的窗口里可以一屏看完；宽松级展开 id 与参数默认值。
正在播放的动作会高亮并在卡片底部显示进度条。

### 新增动作

只往 `src/domain/actionLibrary.ts` 的 `ACTION_LIBRARY` 追加对象，引擎与 Jev 侧零改动：

```ts

  label: '敬礼',
  aliases: ['敬礼', 'salute'],
  description: '右手举至额前行礼。',   // 喂给代码路由，不进 Jev prompt
  actuators: ['arm', 'head'],
  durationMs: 1200,
  interruptible: false,
  priority: 60,
  params: [ /* 参数 schema */ ],
  keyframes: [
    { t: 0,   pose: { shoulder: 0,  elbow: 10 } },
    { t: 0.4, pose: { shoulder: 110, elbow: 95, headPitch: -5 } },
    { t: 1,   pose: { shoulder: 0,  elbow: 10 } },
  ],
  emotion: 'neutral',
}
```

1. 在 `src/jev/robotQuestions.ts` 的 `ROBOT_INTENTS` 加枚举值
2. 在 `buildIntentQuestion()` 的 `criteria` 加中文描述（**这段会发给 Jev，语义必须写全**）
3. 在 `src/jev/actionRouter.ts` 的 `PLANS` 加对应编排与话术，
   并声明 `risk` 与 `requires`——**漏声明 `requires` 会被测试第 8 组拦下**，
   因为它会让安全闸门与拒绝话术都拿不到真实原因
4. 若该意图需要特定硬件，同时在 `CAPABILITY_KEYWORDS` 补关键词，
   让 `requested_capabilities` 能推断出这项需求（安全闸门据此判断）

### 执行引擎要点

- **帧驱动**：外层 `requestAnimationFrame` 调 `tick()`，引擎内部不开定时器
- **串行单槽**：动作按队列依次执行，动作间的 `delayMs` 在槽内等待
- **两种入队语义**：`queue` 追加队尾，但若新编排优先级更高且当前动作可打断则就地抢占；
  `preempt` 是紧急语义，无条件打断当前动作——停止指令走这条，
  对能移动的底盘，"停下"不能排在队尾等前面的动作播完
- **按真实时间插值**：关键帧 `t` 不等分时也能正确还原节奏（用二分查找分段插值）
- **平滑衔接**：动作入场用 easeOut 消化与上一动作终态的偏差，终态严格等于末关键帧
- **参数化解算**：移动/转向的目标位姿由 params 决定，按进度插值到位
- **物理限位**：所有姿态经 `clampPose` 收敛到物理行程内

## 防御性设计

- Jev 响应一律经 `asChoiceAnswer` / `asNoulAnswer` / `asScoreAnswer` 收敛，字段缺失给安全默认
- 意图 choice 收敛到受支持枚举；非法值按**合法候选内部的重算集中度**评估，
  而不沿用为非法选项算出的 confidence
- 请求带超时与指数退避重试，429/529 自动重试
- Jev 不可用时降级到本地规则编排，机器人不会"哑火"
- 硬件缺失时自动剔除对应动作，并说明缺什么、给出不依赖该硬件的替代
- 低电量（<15%）自动禁用底盘动作
- 动作编排保证至少含一个动作，避免机器人无反应
- 摇摆区间在配置读取时重新校验，非法区间回落默认，避免安全判定落不进任何分支
- 配置读取失败回落默认值，localStorage 不可用时静默降级

## 已知边界

- 意图到动作的映射是硬编码的规则表。Jev 只做意图判定，不生成动作编排——
  这是非生成式模型的固有约束，也是可预测性的来源。
- 若需要开放式的话术生成，可在 Jev 判定之后再串一个生成式 LLM，
  输入是已确定的 intent + emotion + 动作编排，输出才是自然语言。
- Jev 只接受文本 / JSON / 文本数组，不支持图像、音频、视频输入。
